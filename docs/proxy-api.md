# Проксі «Відбій» — контракт API (v1)

Проксі стоїть між застосунком і [ukrainealarm](ukrainealarm-api.md). Його задачі:

- тримати ключ API подалі від телефона;
- знати стан повітряних тривог по всій країні: з вебхуків і щохвилинного знімка;
- віддавати цей стан телефонам, не знаючи, який регіон цікавить конкретного користувача (NFR-4).

Базова адреса: `https://vidbiy-proxy.nazar-dev.workers.dev`

```
ukrainealarm ──вебхук на кожну зміну───► POST /webhook ──┐
             ◄──GET /api/v3/alerts раз на хв── Durable Object (стан регіонів)
                                                  │
телефон ──► GET /v1/alerts (у момент будильника й кожні 30 с під час очікування)
```

Версію має лише маршрут, яким користується телефон. Службові маршрути (`/webhook`, `/stats`)
бачимо тільки ми й ukrainealarm, тож вони без версії.

## `GET /v1/alerts`

Усі регіони з активною **повітряною** тривогою та її рівнями. Фільтрацію «громада → район →
область», вибір рівня й правило 24 год робить телефон (див. `requirements.md`, FR-27).

```json
{
  "v": 1,
  "alerts": [
    { "region": "54", "levels": [
        { "level": "red",    "since": "2026-09-27T10:40:00.000Z", "reason": "Ракетна загроза (червоний рівень)" },
        { "level": "yellow", "since": "2026-09-27T09:12:00.000Z", "reason": null } ] },
    { "region": "564", "levels": [
        { "level": "yellow", "since": "2026-09-27T10:18:21.622Z", "reason": null } ] }
  ],
  "confirmed_at": "2026-09-27T11:30:04.214Z",
  "age_seconds": 12
}
```

| Поле | Значення |
|---|---|
| `v` | Версія формату. Зараз `1` |
| `alerts` | Регіони з тривогою, відсортовані за номером. `[]` або `null`, див. нижче |
| `alerts[].region` | ID регіону в нумерації довідника застосунку (`regions.json`). Крим: 9999 в ukrainealarm → `29` |
| `alerts[].levels` | Щонайменше один рівень. Червоний і жовтий можуть діяти одночасно; червоні йдуть першими |
| `level` | `red` (ракетна загроза) або `yellow` (дронова загроза) |
| `since` | Коли цей рівень оголосили. Для правила 24 год |
| `reason` | Текст від ukrainealarm, лише для показу. Буває `null` — рішення від нього не залежить |
| `confirmed_at` | Коли стан востаннє підтвердився (див. «Свіжість») |
| `age_seconds` | Скільки секунд минуло від `confirmed_at` на момент відповіді |

Відповідь завжди `200`. Стан описують поля, а не HTTP-код: застосунку потрібні дані
для рішення, а не помилка транспорту.

### `[]` і `null` — різні стани

- `"alerts": []` — **ми на зв'язку, тривог немає.**
- `"alerts": null` — **ми не знаємо.** Проксі ще жодного разу не завантажив знімок
  (щойно розгорнутий, немає ключа, ukrainealarm відмовив) або Durable Object недосяжний.
  Застосунок дзвонить за fail-safe.

### Незнайомий рівень

Якщо ukrainealarm пришле рівень, відмінний від `Red`/`Yellow`, або тривогу без рівнів,
проксі віддає її як `red`. Тривога з невідомим рівнем — усе одно тривога, і найсуворіше
тлумачення тут безпечніше, ніж загубити її.

### Свіжість (FR-30)

`confirmed_at` — остання успішна звірка з API (знімок `/alerts`), яку вебхуки
продовжують, але **не далі ніж на 15 хв**:

```
confirmed_at = max(остання звірка, min(останній вебхук, остання звірка + 15 хв))
```

- Лише знімок підтверджує повну картину: тиша по конкретному регіону нічого не доводить.
- Вебхуки з будь-яких регіонів доводять, що канал живий; загублених вебхуків за вимірами
  не було (0 підтверджених розбіжностей на сотнях вебхуків). Тож короткому збою `/alerts`
  довіряємо, довгому — ні.
- Вночі вебхуків може не бути до ~25 хв, тож самі вони свіжість не втримають.

Телефон додає до `age_seconds` власний час, виміряний монотонним лічильником
(`SystemClock.elapsedRealtime()`), а не годинником:

```
вік = age_seconds + (скільки минуло на телефоні від моменту відповіді)
```

Понад **3 хв** — дані застарілі (FR-31). Відповідь віддається з `Cache-Control: no-store`:
проміжний кеш повернув би стару відповідь зі старим `age_seconds`.

### Скільки це запитів до ukrainealarm

Запити телефонів до ukrainealarm не йдуть: хоч скільки телефонів питає `/v1/alerts`,
проксі відповідає зі свого стану. Сам проксі бере повний `/api/v3/alerts` **раз на хвилину**
(`src/reload.ts`). Якщо ключ почав відмовляти (3 відмови поспіль або 7 із останніх 30),
проксі на годину переходить на раз на 5 хв, а потім пробує щохвилинний розклад знову.

Поверх цього — **запобіжник** (`src/budget.ts`): не більше 3 запитів за будь-які 60 с
і 3000 за добу, хоч би що сталося в логіці.

Ліміт ключа не опублікований. Виміряно: запит через 18 с після попереднього отримав 401,
через 30 с і 60 с — проходили. `401` від ukrainealarm буває саме через частоту, а не через ключ.

## `POST /webhook`

Сюди ukrainealarm надсилає події. Застосунок цим маршрутом не користується.

Підпис (RSA-SHA256 над `{X-Webhook-Timestamp}.{сире тіло}`) перевіряється публічним ключем
ukrainealarm ще у воркері, до Durable Object. Повідомлення, старші за 5 хв, відкидаються.

| Відповідь | Коли |
|---|---|
| `200 {"ok": true, "outcome": ...}` | Подію прийнято. `outcome`: `changed`, `unchanged`, `out_of_order` або `ignored` (не повітряна тривога чи тестовий регіон) |
| `401` | Немає підпису, він не сходиться або повідомлення застаріле |
| `400` | Підпис правильний, але тіло не схоже на подію |
| `503` | Не вдалося зберегти. Якщо ukrainealarm повторює доставку, хай повторить |

Стан регіону завжди **замінюється** на `activeAlertLevels` з події: `DEACTIVATE` може зняти
одну загрозу, поки інша триває. Зміна набору рівнів без зміни «є/немає тривоги» — теж
`changed`. Кожен регіон пам'ятає `createdAt` останньої застосованої події, і старіші
відкидаються: дублікати, повтори й перемішаний порядок не повертають старий стан.

## `GET /stats`

Діагностика для нас: потік вебхуків (`webhooks`: кількість, паузи, затримка, останні 30),
запити до ukrainealarm (`upstream`), розклад знімків (`reload`), `confirmed_at`. Лише публічна інформація про тривоги,
нічого про користувачів.

## `GET /health`

```json
{ "ok": true, "mock": false, "configured": true, "fake_upstream": false }
```

`configured: false` — на воркері не заданий `UKRAINEALARM_TOKEN`: знімок неможливий,
і `/v1/alerts` завжди віддає `alerts: null`.

## `GET /mock` — лише в mock-режимі

Доступний, тільки якщо воркер запущений із `MOCK=1` (локальна розробка). У продакшні
маршруту не існує.

```
curl.exe "http://127.0.0.1:8787/mock?scenario=alert&uid=16"                  # червона тривога в регіоні 16, щойно
curl.exe "http://127.0.0.1:8787/mock?scenario=alert&uid=16&level=yellow"      # жовта
curl.exe "http://127.0.0.1:8787/mock?scenario=alert&uid=16&started_hours_ago=25"  # триває понад добу
curl.exe "http://127.0.0.1:8787/mock?scenario=clear"                          # відбій
curl.exe "http://127.0.0.1:8787/mock?scenario=down"                           # тривога є, але 10 хв тиші
curl.exe "http://127.0.0.1:8787/mock"                                         # поточний сценарій
```

`down` свідомо лишає тривогу: застосунок має задзвонити саме через застарілі дані,
а не тому, що «все чисто». Сценарій зберігається у сховищі Durable Object і переживає
і засинання об'єкта, і перезапуск `wrangler dev`.

## Звідки взялися ці рішення

- **Один Durable Object на весь світ.** Cloudflare піднімає багато ізолятів воркера;
  стан у пам'яті кожного був би свій. Durable Object існує в одному екземплярі, тож
  вебхуки й телефони бачать один стан. Він лежить у сховищі, бо об'єкт засинає між запитами.
- **Вебхуки + щохвилинний знімок.** Вебхуки дають швидкість (затримка в середньому ~13 с,
  до 85 с), знімок — повноту й свіжість. `/alerts/status` не допомагає: номер зміни
  рухається щосекунди, тож «номер той самий» не трапляється ніколи. Код перевірки
  лишається (`src/check.ts`) як запасний варіант.
- **Сирі факти, правила — на телефоні.** Проксі не знає ні регіону, ні вибраного рівня,
  ні правила 24 год. Уся логіка рішення живе в одному місці — у застосунку.
