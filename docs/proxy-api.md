# Проксі «Відбій» — контракт API

Проксі стоїть між застосунком і [ukrainealarm](ukrainealarm-api.md). Його задачі:

- тримати ключ API подалі від телефона (NFR-4);
- приймати вебхуки ukrainealarm і тримати з них стан тривог по всій країні;
- віддавати цей стан телефонам, не знаючи, який регіон цікавить конкретного користувача.

Базова адреса: `https://vidbiy-proxy.nazar-dev.workers.dev`

```
ukrainealarm ──вебхук на кожну зміну──────► POST /v2/webhook ─┐
             ◄──/alerts/status, коли тихо── Durable Object ◄───┘
                                              │ стан регіонів
                                              ▼
                    телефон ──► GET /v2/alerts (кожні ~30 с під час очікування)
```

## `GET /v2/alerts`

Повертає всі регіони з активною **повітряною** тривогою. Регіон користувача сервер не знає
й не бачить: фільтрацію «громада → район → область» робить телефон.

```json
{
  "v": 2,
  "active": ["16", "124", "1293"],
  "heard_at": "2026-09-24T19:18:37.231Z",
  "age_seconds": 12
}
```

| Поле | Значення |
|---|---|
| `v` | Версія формату. Зараз `2` |
| `active` | ID регіонів із тривогою, у нумерації довідника застосунку (`regions.json`). `[]` або `null`, див. нижче |
| `heard_at` | Коли стан востаннє **підтвердився**: перевірений вебхук, перевірка на тиші або повне завантаження |
| `age_seconds` | Скільки секунд минуло від `heard_at` на момент відповіді |

Відповідь завжди `200`. Стан описують поля, а не HTTP-код: застосунку потрібні дані
для рішення, а не помилка транспорту.

### `[]` і `null` — це різні стани

- `"active": []` — **ми на зв'язку, тривог немає.** Будильник дзвонить, бо все чисто.
- `"active": null` — **ми не знаємо.** Проксі ще жодного разу не завантажив початковий стан
  (щойно розгорнутий, не заданий ключ, ukrainealarm відмовив) або Durable Object недосяжний.
  Будильник дзвонить за fail-safe (NFR-1).

Результат однаковий — дзвонимо, — але причини різні, і плутати їх не можна.

### Звідки береться свіжість

`age_seconds` — це час від останнього **підтвердження**, що стан правильний. Підтвердження бувають трьох видів:

1. **Вебхук.** Прийшла подія з будь-якого регіону — канал живий.
2. **Перевірка на тиші.** Якщо 60 с не було жодного підтвердження, проксі сам питає
   `/api/v3/alerts/status` — номер останньої зміни в ukrainealarm. Цей номер — це .NET ticks
   моменту зміни (не задокументовано, але перевірено), тож його можна порівняти з вебхуками:
   - номер той самий, що минулого разу → нічого не сталося, стан підтверджено;
   - номер новий, але його час не пізніший (±2 с) за найсвіжішу подію, яку ми отримали
     вебхуком → усі зміни ми бачили, стан підтверджено;
   - номер новіший за побачені вебхуки → якусь подію ми пропустили, проксі бере повний
     `/api/v3/alerts` і лише тоді оновлює `heard_at`;
   - API не відповів → `heard_at` **не** оновлюється, наступна спроба за хвилину.
3. **Звірка раз на 10 хв**: повний список, навіть коли вебхуки йдуть безперервно, — страховка
   від загубленого вебхука.

Повний список — дорогий запит: коли ми брали його щохвилини, приблизно кожен третій
отримував 401 (ліміт ukrainealarm). Тому він має власний обмежувач: не частіше ніж раз
на 2 хв, після відмови — пауза 3 хв. Поки обмежувач не пускає, стан не підтверджується,
і якщо так триватиме понад 3 хв, застосунок задзвонить за fail-safe.

Тиша на вебхуках сама по собі нічого не означає: вночі подій може не бути годинами,
і тривога в регіоні при цьому триває. Застарілими дані стають, лише коли **ні вебхуки,
ні перевірки** не підтверджують стан понад 3 хв (NFR-1) — тоді будильник дзвонить.

Скільки це запитів до ukrainealarm:

| Ситуація | Запитів |
|---|---|
| Старт (стану ще немає) | 2: `status` + `alerts` |
| Тихо або всі зміни прийшли вебхуками | 1 `status` на хвилину, лише коли хвилину не було вебхуків |
| Звірка | 1 `alerts` раз на 10 хв |
| Вебхуки зламалися, події відбуваються | 1 `status` на хвилину + 1 `alerts` на 2 хв |
| API не відповідає | 1 на хвилину |

Поверх цього діє **запобіжник** (`server/src/budget.ts`): не більше 3 запитів за будь-які 60 с
і 3000 за добу, хоч би що сталося в логіці. Запити телефонів до API не йдуть: хоч скільки
телефонів питає `/v2/alerts`, проксі відповідає зі свого стану.

Телефон, як і раніше, додає до `age_seconds` власний час, виміряний монотонним лічильником
(`SystemClock.elapsedRealtime()`), а не годинником:

```
вік = age_seconds + (скільки минуло на телефоні від моменту відповіді)
```

Відповідь віддається з `Cache-Control: no-store`: проміжний кеш повернув би стару відповідь
зі старим `age_seconds`, і вік даних став би брехнею.

## `POST /v2/webhook`

Сюди ukrainealarm надсилає події. Застосунок цим маршрутом не користується.

Підпис (RSA-SHA256 над `{X-Webhook-Timestamp}.{сире тіло}`) перевіряється публічним ключем
ukrainealarm ще у воркері, до Durable Object. Повідомлення, старші за 5 хв, відкидаються.

| Відповідь | Коли |
|---|---|
| `200 {"ok": true, "outcome": ...}` | Подію прийнято. `outcome`: `changed`, `unchanged`, `out_of_order` або `ignored` (не повітряна тривога чи тестовий регіон) |
| `401` | Немає підпису, він не сходиться або повідомлення застаріле |
| `503 {"error": "retry_probe"}` | Навмисна відмова, коли ввімкнено `WEBHOOK_RETRY_PROBE` (див. нижче). Подію при цьому застосовано |
| `400` | Підпис правильний, але тіло не схоже на подію |
| `503` | Не вдалося зберегти. Якщо ukrainealarm повторює доставку, хай повторить |

Стан регіону завжди **замінюється** на `activeAlertLevels` з події: `DEACTIVATE` може зняти
одну загрозу, поки інша триває. Кожен регіон пам'ятає `createdAt` останньої застосованої події,
і старіші відкидаються: так дублікати, повтори й перемішаний порядок доставки не можуть
повернути старий стан.

## `GET /v2/stats`

Статистика потоку вебхуків — дані для рішення, чи вистачає самих вебхуків.

```json
{
  "synced_at": "2026-09-24T19:20:00.000Z",
  "heard_at": "2026-09-24T21:03:11.000Z",
  "seconds_since_last_webhook": 14,
  "active_regions": 41,
  "webhooks": {
    "since": "2026-09-24T19:21:05.000Z",
    "received": 312,
    "changed": 140,
    "out_of_order": 0,
    "gaps": { "under1m": 250, "under3m": 55, "under10m": 6, "under30m": 0, "over30m": 0 },
    "max_gap_seconds": 412,
    "max_gap_ended_at": "2026-09-24T20:47:30.000Z",
    "delay_avg_seconds": 1,
    "delay_max_seconds": 3,
    "recent": [ { "receivedAt": "...", "regionId": "124", "alarmType": "AIR", "status": "Activate",
                  "active": true, "delaySeconds": 1, "outcome": "changed" } ]
  }
}
```

Крім того, у відповіді є:

- **`upstream`** — запити до ukrainealarm: `mode` (`live`, `no_token` або `fake`), скільки
  за останню хвилину й за добу, скільки не пустив запобіжник, останні 20 з результатом.
- **`retry_probe`** — результати перевірки повторної доставки.
- **`last_check_at`**, **`last_action_index`** — остання звірка з API.

На що дивитися:

- **`gaps`** — паузи між сусідніми вебхуками. Кожна пауза з `under10m`, `under30m`, `over30m`
  означає, що застосунок у цей час вважав би дані застарілими й дзвонив би за fail-safe.
- **`delay_*`** — від події в ukrainealarm до нас. NFR-3 дає на весь шлях до дзвінка 2 хв.
- **`out_of_order`** — чи буває перемішаний порядок доставки.

Тут лише публічна інформація про тривоги, нічого про користувачів.

## Перевірка повторної доставки вебхуків

Змінна `WEBHOOK_RETRY_PROBE=N`: кожну N-ту подію проксі застосовує як завжди, але відповідає `503`.
Якщо те саме тіло (за SHA-256) прийде знову, `retry_probe.redelivered` зросте, а в
`redelivery_delays_seconds` буде видно, через скільки секунд повторили.

Ризик: після кількох відмов відправник може вирішити, що наша адреса мертва, й відписати нас.
Тому N варто брати великим (наприклад, 50) і вимикати перевірку, щойно з'явиться відповідь.

## Сухий прогін: `FAKE_UPSTREAM=1`

Запити до ukrainealarm проходять через запобіжник і рахуються в `/v2/stats`, але назовні
не йдуть: `status` отримує вигаданий незмінний номер, `alerts` — порожній список.
Так можна перевірити розклад запитів на розгорнутому воркері, не ризикуючи ключем.
**У цьому режимі проксі каже телефонам «тривог немає»** — будильник дзвонить одразу,
тобто поводиться як звичайний.

Без ключа (`UKRAINEALARM_TOKEN` не заданий) запити теж лише рахуються, але стан лишається
невідомим (`active: null`).

## `GET /health`

```json
{ "ok": true, "mock": false, "configured": true, "fake_upstream": false }
```

`configured: false` означає, що на воркері не заданий `UKRAINEALARM_TOKEN`: початковий
знімок неможливий, і `/v2/alerts` завжди віддає `active: null`.

## `GET /mock` — лише в mock-режимі

Доступний, тільки якщо воркер запущений із `MOCK=1` (локальна розробка). У продакшні
маршруту не існує. Дозволяє керувати станом вручну й перевіряти телефон без справжніх подій:

```
curl "http://localhost:8787/mock?scenario=alert&uid=16"   # тривога в регіоні 16, дані свіжі
curl "http://localhost:8787/mock?scenario=clear"          # відбій
curl "http://localhost:8787/mock?scenario=down"           # тривога лишається, але 10 хв тиші
```

`down` свідомо лишає тривогу: застосунок має задзвонити саме через застарілі дані,
а не тому, що «все чисто».

Сценарій зберігається у сховищі Durable Object, тож переживає і засинання об'єкта,
і перезапуск `wrangler dev`. `GET /mock` без параметрів показує поточний сценарій.

## Звідки взялися ці рішення

- **Один Durable Object на весь світ.** Cloudflare піднімає багато ізолятів воркера;
  стан у пам'яті кожного був би свій. Durable Object існує в одному екземплярі,
  і вебхуки та телефони бачать один і той самий стан. Він лежить у сховищі об'єкта,
  бо об'єкт засинає між запитами.
- **Вебхук замість опитування.** alerts.in.ua рахував ліміт за IP, а запити з Workers до
  сайтів за Cloudflare приходять зі спільних внутрішніх адрес — ми ділили ліміт із чужими
  воркерами й ловили 429. Вебхук обертає напрямок: зміни приходять до нас самі,
  а самі ми питаємо лише тоді, коли тихо, — щонайбільше раз-два на хвилину.
- **Початковий знімок.** Вебхук надсилає лише зміни; без знімка регіон, де тривога
  почалася до підписки, вважався б чистим.
- **Перевірка на тиші.** Перша версія v2 рахувала свіжість лише від вебхуків і вважала
  тишу поломкою. Вночі це означало б хибний дзвінок посеред тривоги, що триває.
